# Applications Android hybrides (WebView + serveur HTTP Ocara embarqué)

## Fondations — Fait, vérifié (pont JNI + squelette Gradle, APK réel produit)

Voir "Ce qui manque" ci-dessous, points 1 et 2 : **faits et vérifiés**. Le reste (points 3-5 : cleartext HTTP, permission, cycle de vie) est traité de façon minimale mais fonctionnelle pour ce squelette — voir le détail plus bas.

**Bilan global à ce stade** : fonctionne bout en bout sur un émulateur x86_64 accéléré (voir "Test réel sur émulateur"). Sur un **appareil physique réel** (voir "Test réel sur appareil physique") : le crash au démarrage est **corrigé et vérifié** ([runtime-android-exit-unsafe](runtime-android-exit-unsafe.md), clos), l'accès aux fichiers statiques (`public/`) est **corrigé et vérifié** (voir "Fichiers statiques Android — Fait, vérifié" plus bas), la redirection vers le navigateur externe au clic sur un lien/à la soumission d'un formulaire est **corrigée et vérifiée** (voir "WebView : navigation redirigée vers le navigateur externe — Fait, vérifié"). Un **quatrième bug distinct**, découvert seulement après que les trois problèmes ci-dessus ont cessé de le masquer (la page HTML rendue était corrompue, un grand nombre à la place du contenu), est **corrigé** — cause racine réelle : les pointeurs de tas Android (Scudo) portent un tag dans leur octet de poids fort depuis Android 11, jamais un bug de codegen comme d'abord supposé — voir [runtime-android-aarch64-pic-string-concat](runtime-android-aarch64-pic-string-concat.md). Reste seulement une reconfirmation en exécution réelle (aucun appareil connecté au moment du correctif).

## Idée

Rendre un programme Ocara du style [examples/advanced/mini_project](../../examples/advanced/mini_project) (serveur `ocara.HTTPServer` + contrôleurs/modèles + templates HTML rendus côté serveur) **fonctionnel sur Android**, en l'affichant dans une `WebView` Android système pointée sur le serveur HTTP embarqué (`http://127.0.0.1:<port>/`) — même principe que Cordova/Capacitor, ou que ce que Tauri fait sur desktop (une fenêtre native + un moteur web, mais le "backend" est du code Ocara natif, pas du JS).

C'est un point de départ délibérément plus étroit et plus sûr que le support SDL/GUI native (voir [packaging-android](packaging-android.md) sous-chantier 4 et le ticket suivant sur la GUI native) : **aucune dépendance à SDL3, GTK ou Tauri** — un serveur HTTP est juste des sockets, déjà vérifié comme cross-compilable pour Bionic ([packaging-android](packaging-android.md) sous-chantier 3, `ocara_runtime` de base). Le morceau réellement nouveau ici est le pont JNI + le squelette Android (Activity/WebView/Gradle), pas le runtime Ocara lui-même.

## Ce qui est déjà en place (vérifié par [packaging-android](packaging-android.md))

- Cross-compilation Cranelift vers `aarch64-linux-android` (sous-chantier 1).
- `ocara_runtime` (donc `ocara.HTTPServer`, sockets, SQLite, HTML) compile pour Bionic (sous-chantier 3).
- Liaison en `.so` partagé, PIC, sans `DT_TEXTREL`, chargeable par le dynamic linker Bionic (sous-chantier 2).
- Un `.so` Ocara exporte déjà `main`/`__fn_wrap_main` comme symboles ordinaires (confirmé par `objdump -t` lors de la vérification du sous-chantier 2) — un point d'entrée qu'un pont JNI peut appeler directement, sans modification du compilateur.

## Ce qui manque, non vérifié (état avant travail) / Ce qui a été fait

1. **Pont JNI — Fait.** Nouveau crate `runtime_android_jni` (staticlib, dépendance `jni` — wrapper JNI sûr ; un premier essai avec `jni-sys` brut a été abandonné après un SIGSEGV sur appareil réel, voir [runtime-android-exit-unsafe](runtime-android-exit-unsafe.md)). Expose `Java_com_ocara_bridge_OcaraBridge_nativeStartServer` (convention de nommage JNI, classe Java figée plutôt que configurable — voir la doc du crate) : lance `main()` du programme Ocara lié dans le même `.so` sur un thread séparé, fire-and-forget. **Piège réel rencontré** : rien ne référence ce symbole ailleurs dans le `.so` (seule la JVM l'appelle, dynamiquement, à l'exécution) — l'extraction paresseuse habituelle d'une archive `.a` le laissait silencieusement de côté (confirmé par reproduction : absent de `nm -D` sur le premier essai). Corrigé avec `-Wl,-u,<symbole>` dans `link_android` (nouveau paramètre `jni_bridge_lib` + flag CLI `--android-jni-bridge`), qui force son extraction même sans référence entrante.
2. **Squelette Android (Activity + Gradle) — Fait.** `packaging/android/` : projet Gradle réel (scaffoldé via l'outil `android` du SDK, template `empty-activity`, Compose), simplifié à l'essentiel — `MainActivity.kt` démarre le pont JNI puis sonde `http://127.0.0.1:8081/` avant d'afficher une `WebView` (`AndroidView` Compose) dessus, `OcaraBridge.kt` déclare le pont côté Kotlin.
3. **Cleartext HTTP local — Traité, scope minimal.** `network_security_config.xml` autorise le HTTP en clair, mais UNIQUEMENT vers `127.0.0.1` (pas un `usesCleartextTraffic` global) — fonctionne sur le `minSdk` retenu (24 ; Network Security Config existe depuis l'API 24). Pas d'alternative HTTPS explorée, jugée inutile pour une boucle locale scoped ainsi.
4. **Permission réseau — Fait.** `<uses-permission android:name="android.permission.INTERNET" />` dans le manifeste.
5. **Cycle de vie Android — PAS traité**, comme anticipé : le pont reste fire-and-forget (aucun arrêt propre du serveur natif à la fermeture de l'Activity, aucune notification "serveur prêt" autre que le sondage HTTP côté Kotlin).

## Adaptation réelle de `examples/advanced/mini_project` — Fait, vérifié

**Terminé, puis simplifié.** Une première version introduisait un second point d'entrée dédié, `main_android.oc` (même application que `main.oc` — mêmes `configs/`/`controllers/`/`models/`/`services/`/`templates/`, même base SQLite — mais sans `ocara.Tauri`, `main` appelant directement `server.start()`). **David a ensuite fusionné les deux** en un unique `main.oc` multi-plateforme (`main_android.oc` supprimé) : une branche `if System::OS equal "android" { server.start(); result 0 }` en tête de `main` court-circuite le sondage HTTP + `ocara.Tauri` (déjà hors du thread UI Android grâce au pont JNI, donc pas besoin du sous-thread + sondage que fait la version desktop pour ne pas geler une fenêtre Tauri ouverte trop tôt) — une seule source portable au lieu de deux fichiers à maintenir en parallèle. (Import manquant `ocara.System` ajouté à cette occasion — `System::OS` est utilisé mais n'était pas importé.)

### Vérification

- **Sur l'hôte d'abord** (avant tout effort de cross-compilation, pour isoler les bugs applicatifs des bugs Android) : compilé et exécuté directement, `curl http://localhost:8081/` répond `HTTP 200` avec le vrai HTML rendu (liste de voitures, SQLite, templates) — confirme que l'adaptation du point d'entrée n'a rien cassé.
- **Cross-compilé et lié pour Android** avec `--android-jni-bridge`, même rigueur que le reste du chantier : `.so` ELF `DYN` AArch64, **aucun `DT_TEXTREL`**, `main` et `Java_com_ocara_bridge_OcaraBridge_nativeStartServer` tous deux exportés.
- **APK réel construit** (`./gradlew assembleDebug`, `BUILD SUCCESSFUL`) avec ce `.so` — taille APK ~67 Mo (contre ~40 Mo pour le squelette de démonstration avec un serveur vide), cohérent avec une vraie application (contrôleurs, modèles, templates HTML, SQLite) plutôt qu'un stub.

### Fichiers statiques Android — Fait, vérifié

Constat initial (pendant l'adaptation) : `self.rootPath("./public/")` (`configs/Server.oc`, sert `style.css`) ne fonctionnait PAS sur un appareil réel — `ocara.HTTPServer` lit ces fichiers avec les API fichier standard (`std::fs`), qui ne voient pas les assets packagés par Gradle (`app/src/main/assets/`, accessibles uniquement via l'API NDK `AAssetManager`, un mécanisme distinct d'un chemin de système de fichiers classique). Les pages HTML dynamiques restaient intactes (templates désucrés à la compilation par `HTML::renderFile` en chaînes littérales embarquées dans le `.so`) — seule la feuille de style externe était concernée.

**Corrigé** en réutilisant le même principe que le chemin SQLite (voir "chdir vers `Context.getFilesDir()`" plus bas) plutôt qu'en apprenant à `ocara.HTTPServer` à parler `AAssetManager` (aurait exigé une branche Android dans le runtime lui-même, pour un mécanisme entièrement propre à cette plateforme) : `MainActivity.onCreate()` (`copyAssetsToFilesDir()`, voir `packaging/android/app/src/main/java/com/ocara/demo/MainActivity.kt`) copie récursivement tout `app/src/main/assets/` vers `filesDir` (donc, après le `chdir()` du pont JNI, vers le même répertoire de travail que `"./app.db"`) à chaque lancement de l'Activity, AVANT `nativeStartServer`. `self.rootPath("./public/")` retrouve alors un vrai chemin de système de fichiers ordinaire, exactement comme sur desktop.

**Étape manuelle documentée** (demande explicite : ce n'est PAS automatisé par le build) : tout fichier statique servi par `rootPath` (CSS, images, etc.) doit être copié à la main sous `packaging/android/app/src/main/assets/` avant `./gradlew assembleDebug` — Gradle ne sait pas qu'un projet Ocara a un dossier `public/` à embarquer. Voir `packaging/android/README.md`, section "Fichiers statiques".

Vérifié sur le vrai appareil (Realme RMX3834) : `curl` via `adb forward` sur `/style.css` répond `HTTP 200` avec le contenu réel du fichier (pas un 404).

## Test réel sur émulateur — Fait, vérifié

**Terminé.** Le SDK Android fournit un vrai gestionnaire d'émulateurs (`android emulator create/start/stop/list`), et **KVM est disponible sur cet environnement** (`/dev/kvm` accessible) — un émulateur **x86_64** (accélération matérielle complète) a été créé, démarré (headless, ~80s de démarrage, confirmant une vraie accélération), et utilisé pour un test réel de bout en bout, pas seulement de l'inspection statique.

Piège d'ABI important : l'APK ne contenait qu'un `.so` **arm64-v8a**. Un hôte x86_64 émule de l'ARM64 en traduction logicielle pure (pas d'accélération KVM pour une ISA différente de celle de l'hôte), potentiellement très lent — la bonne combinaison pour un test rapide et réactif est un système x86_64 (accéléré) + un `.so` **x86_64**. `ocara` supporte déjà `--target x86_64-linux-android` nativement (le backend x86 de Cranelift est déjà embarqué via `host-arch`, cet hôte étant lui-même x86_64 — aucune feature Cargo supplémentaire à activer, contrairement à `arm64` pour le sous-chantier 1). Les cibles Make (`build-runtime-android`, `build-jni-bridge-android`, `build-runtime-sdl-android`) ont été rendues paramétrables (`ANDROID_TARGET`, défaut `aarch64-linux-android`) pour cross-compiler aussi vers `x86_64-linux-android` sans dupliquer chaque cible.

Nouvelle cible **`make android-simulator <apk>`** (voir `Makefile`) : vérifie qu'un AVD existe (le crée sinon), qu'un émulateur tourne réellement (`adb devices`, pas la colonne Status de `emulator list` qui ne reflète pas l'état réel), désinstalle une éventuelle version déjà installée (purge données/cache) pour repartir d'un état propre, installe l'APK, puis le lance (`monkey -c android.intent.category.LAUNCHER`, sans avoir besoin de connaître le nom exact de l'Activity).

### Deux bugs réels trouvés et corrigés grâce à ce test (invisibles par inspection statique)

Le premier lancement de l'APK **plantait** (`SIGABRT`), un résultat que ni la vérification statique ni les tests hôte n'auraient jamais pu révéler :

1. **`System::OS` ne reconnaissait pas Android.** `runtime/src/lib.rs`, `__system_os()` : `cfg!(target_os = "linux")` est **`false`** pour une cible `aarch64-linux-android`/`x86_64-linux-android` — vérifié (`rustc --print cfg --target x86_64-linux-android` ne donne QUE `target_os="android"`, jamais `"linux"` en plus), alors que le triple contient pourtant le mot "linux". Sans branche dédiée, `System::OS` retournait `"unknown"` sur Android. Corrigé (ajout de `cfg!(target_os = "android")` avant les autres branches) — `docs/builtins/System.md`/`src/builtins/system.rs` mis à jour (`"android"` ajouté aux valeurs possibles).
2. **Chemin SQLite invalide au démarrage.** `configs/Database.oc` retournait `"./app.db"` (chemin relatif) inconditionnellement — sur Android, `SQLite::open()` échouait (répertoire de travail non accessible en écriture), déclenchant `throw_sqlite_exception` → `__ocara_fail` → `std::process::exit`, qui a lui-même révélé un **second problème distinct**, plus profond : la séquence de sortie détruit un mutex encore possédé/contesté (`mutex.cc:432] destroying mutex with owner or contenders`) — glibc tolère silencieusement ce comportement indéfini (UB), Bionic le détecte explicitement et force un `SIGABRT`. Corrigé pour ce ticket en rendant `Database::path()` conditionnel (`if System::OS equal "android"`) vers un chemin absolu dans le bac à sable de l'app (`/data/user/0/com.ocara.demo/app.db`) — **piège concret rencontré en le corrigeant** : un premier essai avec `.../files/app.db` échouait ENCORE, car `files/` n'est créé par Android que lors du premier appel à `Context.getFilesDir()` côté Java (jamais fait ici) — confirmé par reproduction (`adb shell run-as com.ocara.demo ls -la /data/user/0/com.ocara.demo/` : seuls `cache/`/`code_cache/` existent). Le répertoire racine du bac à sable, lui, existe toujours dès l'installation.

Le second problème (destruction de mutex non sûre pendant la sortie sur exception non gérée) n'a PAS été creusé plus loin ici — corrigé indirectement en évitant de déclencher `throw_sqlite_exception` du tout, pas en réparant la séquence de sortie elle-même. Un vrai bug de fiabilité runtime, à part, mériterait sa propre investigation un jour (pourquoi `std::process::exit` interagit avec un mutex encore possédé).

### Vérification finale

Sur l'émulateur x86_64 réel, avec le vrai point d'entrée Android de l'époque (`main_android.oc`, depuis fusionné dans `main.oc`, voir "Adaptation réelle" plus haut) et `Database.oc` (fichiers du dépôt, pas une copie de test) : processus vivant (pas de crash), `adb forward` + `curl http://127.0.0.1:<port-forwardé>/` répond `HTTP 200` avec le vrai titre rendu (`<title>Voitures — Garage Ocara</title>`), fichier SQLite créé exactement à l'emplacement attendu (`adb shell run-as ... ls -la /data/user/0/com.ocara.demo/app.db`).

## Test réel sur appareil physique — Crash corrigé et vérifié ; un nouveau bug distinct découvert ensuite

Testé sur un vrai téléphone (Realme RMX3834, Android 15/API 35, arm64-v8a, branché en USB et détecté automatiquement à côté de l'émulateur), via la même cible `make android-simulator`, étendue avec un paramètre `ANDROID_SERIAL=<serial>` pour cibler un appareil précis au lieu de gérer un AVD.

### Chronologie (deux problèmes trouvés, corrigés, puis un troisième découvert ensuite)

Première tentative, chaîne d'événements observée (données réelles via `adb pull /data/tombstones/...`, pas une supposition) :
1. Premier lancement : `Fatal signal 11 (SIGSEGV)` dans un thread **"Jit thread pool"**, backtrace entièrement à l'intérieur d'ART (`art::jit::JitCodeCache::Commit`, `/apex/com.android.art/lib64/libart.so`) — **sans rapport avec le code Ocara** (le `.so` venait tout juste de finir de charger, rien de notre code n'avait encore eu la main). Vraisemblablement un problème ART/ROM (Realme/ColorOS) préexistant, pas causé par ce projet — jamais revu lors des tentatives suivantes, pas investigué davantage.
2. Android relance automatiquement l'app après ce crash (comportement standard). Cette fois, `Database::connect()` → `SQLite::open()` échouait et l'app replantait — de façon identique après un `pm clear` complet (état totalement propre, élimine l'hypothèse d'un fichier corrompu par le crash précédent).

Ce second crash a révélé un problème plus profond et plus général que le seul chemin SQLite : `__ocara_fail` (le gestionnaire d'exception non rattrapée) appelait `std::process::exit()`, ce qui est sûr sur desktop mais faisait s'effondrer le processus sur Android (`__cxa_finalize` détruit des objets globaux d'ART/`libhwui` jamais conçus pour l'être en cours de vie d'une app). **Corrigé et vérifié** — voir **[runtime-android-exit-unsafe](runtime-android-exit-unsafe.md)** (clos) pour le détail complet : le fix lui-même (`libc::_exit(1)` sur Android), la cause racine réelle de l'échec `SQLite::open()` (résolue en généralisant le mécanisme, voir juste en dessous), et un piège rencontré en cours de route (SIGSEGV introduit par des bindings JNI bruts, corrigé en passant à la crate `jni`).

### `chdir` vers `Context.getFilesDir()` — mécanisme général remplaçant le chemin SQLite conditionnel par OS

La première tentative de correction du chemin SQLite (`Database::path()` conditionnel, `if System::OS equal "android"` vers un chemin absolu construit à la main) fonctionnait sur l'émulateur mais PAS sur l'appareil réel (probablement des restrictions OEM/ColorOS plus strictes que l'AOSP stock). Remplacé par un mécanisme général, plus proche du modèle desktop : le pont JNI (`runtime_android_jni`) reçoit `Context.getFilesDir().getAbsolutePath()` depuis Kotlin (la SEULE API garantissant la création réelle du répertoire ET son étiquetage SELinux correct — pas un chemin deviné côté natif) et fait `chdir()` vers ce répertoire AVANT de démarrer le programme Ocara. `Database.oc` est ainsi redevenu un simple chemin relatif inconditionnel (`"./app.db"`, aucune branche `System::OS`) — exactement comme sur desktop, où le répertoire de travail est celui depuis lequel le programme est lancé. Le même mécanisme sert aussi à résoudre `"./public/"` (voir "Fichiers statiques Android" plus haut).

### WebView : navigation redirigée vers le navigateur externe — Fait, vérifié

Signalé directement par l'utilisateur en testant sur son téléphone : cliquer sur un lien ou valider un formulaire dans la WebView ouvrait le navigateur externe au lieu de rester dans l'app. Cause : sans `WebViewClient` explicitement assigné, le comportement par défaut d'Android est de traiter toute navigation initiée par l'utilisateur comme une intention à résoudre par le système. **Corrigé** en assignant `webViewClient = WebViewClient()` (voir `MainActivity.kt`, `OcaraWebViewScreen()`) — la navigation reste dans la WebView tant que `shouldOverrideUrlLoading` n'est pas explicitement surchargé pour dire le contraire.

### Rendu HTML corrompu, puis corrigé : pointeurs de tas Android tagués (pas un bug de codegen)

Une fois le crash, l'accès à `public/` et la redirection WebView corrigés, un signalement direct de l'utilisateur ("sur le mobile il n'affiche pas la page mais un nombre") a révélé un problème plus profond : la page HTML rendue par le serveur était tronquée et remplacée en partie par un grand nombre à l'allure d'une adresse mémoire, uniquement sur arm64 réel (jamais reproduit sur l'émulateur x86_64 ni sur l'hôte). Une première bissection avait conclu, à tort, à un bug de codegen Cranelift AArch64+PIC. La cause racine réelle, trouvée en lisant le code de classification du runtime : Bionic/Scudo (l'allocateur natif d'Android depuis la version 11) tague l'octet de poids fort des pointeurs de tas — une valeur que `ocara_runtime` interprétait comme un entier brut au lieu d'un pointeur, faute de connaître ce comportement. **Corrigé et vérifié en exécution réelle** en désactivant ce tagging pour tout le processus Ocara (`mallopt(M_BIONIC_SET_HEAP_TAGGING_LEVEL, ...)` dans le pont JNI) — sur le vrai téléphone, `curl` répond désormais `HTTP 200, 2306 octets` avec le HTML complet et correct, taille identique à celle obtenue sur x86_64. Voir le ticket dédié **[runtime-android-aarch64-pic-string-concat](runtime-android-aarch64-pic-string-concat.md)** pour l'analyse complète, le correctif et sa vérification (y compris une fausse alerte de crash rencontrée puis infirmée en cours de route — de vieilles tombstones, pas un vrai crash).

### Import `ocara.Tauri` sur un `main.oc` unifié desktop/Android — corrigé (talon no-op)

En reconstruisant l'exemple pour valider le correctif ci-dessus, la compilation Android de `main.oc` (désormais unifié, voir "Adaptation réelle" plus haut) échouait : le compilateur rejetait catégoriquement toute cible Android référençant `ocara.Tauri`, MÊME derrière `if System::OS equal "android" { ...; result 0 }` (un contrôle statique, pas une analyse d'atteignabilité). **Corrigé sur demande explicite de David** ("Si on compile pour android et qu'il y a Tauri dans le projet, on ignore l'import de Tauri") : `CraneliftEmitter::predeclare_functions` (`src/codegen/emit.d/emitter.rs`, nouveau champ `is_android_target` + `define_stub_function`) compile désormais chaque builtin `Tauri_*` en talon LOCAL no-op (renvoie `0`/rien, jamais un import résolu par `libocara_runtime_tauri.a`/GTK) quand la cible est Android — `src/main.rs` remplace l'ancien rejet catégorique par un simple avertissement (`print_warn`). Le `.o`/`.so` produit ne référence donc plus jamais GTK/WebKit sur Android, tout en restant reconstructible pour desktop sans changement. Vérifié : `.so` sans symbole `Tauri_*` non résolu, sans dépendance GTK/WebKit (`nm -D -u`/`readelf -d`), `make build`/`tests`/`regression` (hôte) inchangés.

## Ce qui reste (hors "fondations", adaptation de mini_project et test émulateur)

- Cycle de vie Android (voir point 5 plus haut) — toujours fire-and-forget, pas d'arrêt propre du serveur natif à la fermeture de l'Activity.
- Aucune visibilité sur les logs/erreurs du runtime Ocara depuis un `.so` Android (le `stderr` d'un `.so` chargé par JNI n'est pas capturé par `logcat`) — a ralenti le diagnostic du crash `__ocara_fail` (tombstones `adb pull` utilisés à la place) ; a aussi ralenti l'isolation du bug de pointeurs tagués (une première hypothèse de codegen, fausse, a dû être écartée en lisant le code plutôt qu'en observant le symptôme — voir aussi la fausse alerte de "nouveau crash" causée par de vieilles tombstones re-signalées par `monkey`, documentée dans ce même ticket).
- Généralisation en builtin `ocara.UIHybrid`, voir [langage-builtin-ui-hybride](langage-builtin-ui-hybride.md) — tout ici reste câblé à la main (port et nom de `.so`/package codés en dur), pas une abstraction du compilateur. (Le point d'entrée est en revanche déjà unifié desktop/Android en un seul `main.oc`, Tauri compris, voir "Adaptation réelle" plus haut.)

## Priorité / Complexité

**Priorité Très Basse** — étape "pour commencer" explicitement voulue par David avant la GUI native. Fondations posées et vérifiées sur émulateur x86_64 (accéléré KVM) **et sur appareil physique réel** (arm64-v8a, Realme RMX3834) : crash au démarrage, accès aux fichiers statiques, redirection WebView et rendu HTML tous corrigés et **vérifiés en conditions réelles** (`HTTP 200, 2306 octets`, identique à x86_64). **Complexité** : le pont JNI, le squelette Gradle et le test émulateur, une fois les bons outils trouvés (le CLI `android`), se sont avérés une **addition contenue** ; les corrections du crash et du `chdir` ont touché un mécanisme plus profond (gestion des exceptions non rattrapées, voir [runtime-android-exit-unsafe](runtime-android-exit-unsafe.md), clos) mais sont restées confinées au runtime/pont JNI, sans toucher au compilateur. Le bug de rendu ([runtime-android-aarch64-pic-string-concat](runtime-android-aarch64-pic-string-concat.md)) s'est avéré, une fois sa vraie cause trouvée, tout aussi contenu : un seul appel `mallopt` dans le pont JNI. Le talon Tauri/Android a, lui, touché le compilateur (`CraneliftEmitter`) — une addition ciblée (une fonction, un champ), pas une réécriture.
