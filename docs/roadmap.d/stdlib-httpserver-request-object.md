# Handler de route `req:int` — devrait être un objet `HTTPServerRequest`

- Nouvelle classe **`HTTPServerRequest`** créée (`src/builtins/httpserver.rs::request_class()`), enregistrée exactement comme les classes existantes à sucre d'instance statique (`allows_instance_sugar`, `src/sema/typecheck.rs`) — même patron que `HTTPRequest`/`SQLite`, PAS le patron de délégation de `HTTPResponse` (`HTTPServerRequest` a ses PROPRES méthodes mangées `HTTPServerRequest_*`, jamais partagées avec `HTTPServer`).
- **Aucun changement d'ABI confirmé** : un paramètre `Type::Named("HTTPServerRequest")` se compile identiquement à l'ancien `req:int` (`IrType::from_ast` réduit tout type nommé à `Ptr`, un seul emplacement i64) — vérifié en pratique via `nameless(req:HTTPServerRequest): int { ... }`, qui fonctionne du premier coup, sans aucune modification du lowering de fermeture (`src/lower/expr.d/nameless.rs`) au-delà de ce qui existait déjà pour `nameless(db:SQLite): void`.
- Toutes les anciennes méthodes STATIQUES (`HTTPServer::path/method/body/header/query/respond/respondHeader(req, ...)`) renommées en méthodes D'INSTANCE sur `HTTPServerRequest` (`req.path()`, `req.respond(...)`, ...) — cassé volontairement, SANS coexistence (comme demandé) : `req:int` ne compile plus, confirmé par la nécessité de migrer tout le corpus existant (voir plus bas).
- `header(name)` vérifié réellement insensible à la casse dans les DEUX sens (nom demandé ET nom stocké) — tiny_http ne normalise jamais la casse d'origine du champ (`h.field.to_string()` reflète exactement ce que le client a envoyé, vérifié en lisant le code appelant avant de le supposer) ; la casse D'ORIGINE est maintenant préservée dans `OcaraHttpContext.headers` (avant ce ticket, elle était perdue au stockage — `.to_lowercase()` appliqué à l'insertion — suffisant pour l'ancien `header(name)` mais aurait cassé la nouvelle `headers()`, qui doit refléter la casse réellement reçue).
- **`req.headers(): map<string, string|int|float|bool|null>`** ajoutée — construite NATIVEMENT côté Rust (`HTTPServerRequest_headers`, même patron que `collect_all_rows` pour SQLite), jamais via une affectation indexée Ocara-level (`m[k]=v`), justement pour ne jamais dépendre du bug de boxing découvert PENDANT ce chantier (voir plus bas).
- **`req.param(key, method = null): mixed`** et **`req.params(): map<string, map<string, mixed>>`** ajoutées avec exactement les 10 buckets `CONNECT/DELETE/GET/HEAD/OPTIONS/PATCH/POST/PUT/QUERY/TRACE`, toujours présents. Règle de précédence de `param()` vérifiée par test bout-en-bout ET tests unitaires : `method` donné → recherche exclusive dans ce bucket ; `method` omis → fusion GET (query string) + méthode réelle (corps), le corps l'emportant sur la query string en cas de collision de clé.
- **`application/x-www-form-urlencoded`** (corps) : ferme aussi
  [stdlib-httpserver-post-body-parsing](stdlib-httpserver-post-body-parsing.md) — voir ce ticket pour son détail, fondu ici comme demandé.
- **`multipart/form-data`** (upload de fichier) — capacité entièrement nouvelle, hors périmètre des deux tickets initiaux, ajoutée à la demande explicite de l'utilisateur dans ce même chantier :
  - Mini-parseur écrit à la main (`parse_multipart`, `runtime/src/httpserver.rs`) plutôt qu'une dépendance externe — vérifié qu'aucune crate de ce projet (`tiny_http`, `ureq`, `url`, `regex`, `serde_json`, `rusqlite`, `mysql` — `runtime/Cargo.toml` entièrement relu) ne fait de parsing multipart, cohérent avec la convention déjà établie par `parse_query`/`url_decode` (également écrits à la main).
  - Tolérance CRLF/LF vérifiée par test unitaire dédié (un corps multipart LF-seul, non conforme à RFC 7578 mais réaliste côté clients tiers, parse identiquement à un corps CRLF strict).
  - **Décision documentée — binarité de `content`** : investigué `ptr_to_str`/`alloc_str` (`runtime/src/lib.rs`) — une `string` Ocara n'est PAS binaire-sûre en lecture : `ptr_to_str` exige de l'UTF-8 valide et retombe SILENCIEUSEMENT sur `""` sinon (`std::str::from_utf8(...).unwrap_or("")`), ce qui aurait corrompu tout upload binaire réel (image, PDF...) dès sa première lecture côté Ocara. Ce projet a déjà une convention établie pour exactement ce cas — `File::readBytes`/`writeBytes` (`array<int>`, un octet par élément, voir `src/builtins/file.rs`/`runtime/src/file.rs`) — réutilisée ici pour `content` plutôt que d'inventer une troisième convention (base64 envisagé puis écarté : il existe déjà une réponse dans ce langage à "comment représenter du binaire", pas besoin d'en ajouter une seconde). Vérifié par reproduction avec un contenu volontairement non-UTF8 (`\xff\xd8\xff\xe0...`, en-tête JPEG réel) via une vraie requête `curl -F`, octet par octet identique en sortie.
  - Le corps de la requête est maintenant lu en octets BRUTS (`read_to_end`, pas `read_to_string`) dans `handle_request` — sans ce changement, un upload binaire aurait fait échouer/tronquer la lecture du corps AVANT même d'atteindre le parseur multipart (`read_to_string` échoue dès le premier octet non-UTF8). `req.body(): string` reste dérivé du même corps brut via une conversion lossy (comportement inchangé pour un corps texte réel, qui est toujours de l'UTF-8 valide).
  - Absence de `Content-Type` sur un part fichier → défaut `"application/octet-stream"`, vérifié par test unitaire dédié.
  - Limitation documentée (pas résolue, comme convenu) : plusieurs parts du même nom (`photos[]` soumis plusieurs fois) → le dernier écrase les précédents, jamais de plantage.
  - Aucune limite de taille de corps ajoutée (pré-existante, tout le corps était déjà lu intégralement en mémoire avant ce ticket) — non aggravée, non résolue, conformément à ce qui était demandé.

## Constat (ticket original)

Les handlers de route enregistrés via `server.route(path, method, handler)` prenaient un paramètre `req:int` — un entier opaque, en réalité un pointeur `OcaraHttpContext*` déguisé (`runtime/src/httpserver.rs:30-33`, signature compilée `extern "C" fn(env_ptr: i64, req: i64) -> i64`). Toutes les méthodes serveur qui en dépendaient (`HTTPServer::path/method/body/header/query/respond/respondHeader`) prenaient ce même entier en premier argument.

Exemple typique (`examples/advanced/mini_project/controllers/CarController.oc`) :
```ocara
public static method show(req:int): int {
    scoped idParam:string = HTTPServer::query(req, "id")
    ...
    HTTPServer::respond(req, 200, html)
    return 0
}
```
Rien dans la signature `req:int` n'indiquait qu'il s'agissait d'une requête HTTP — un appelant pouvait passer n'importe quel entier sans que le typage ne le retienne.

`ocara.HTTPRequest` existait déjà, mais c'est un objet complètement différent (client sortant uniquement).
