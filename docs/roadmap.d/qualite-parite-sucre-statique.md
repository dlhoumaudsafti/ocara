# Parité forme statique / sucre d'instance — tests et robustesse du dispatch de type

## Constat

En corrigeant l'affichage de `Array::get(arr, i)`/`Map::get(m, k)` (voir docs/roadmap.d/langage-array-get-display-bug.md), le correctif n'a d'abord été appliqué qu'à la forme **statique** (`Array::get(arr, i)`, `Expr::StaticCall` dans `expr_ir_type`) — le sucre d'**instance** (`arr.get(i)`, `m.get(k)`, `Expr::Call` avec callee `Expr::Field`) souffrait du **même bug**, non détecté car quasiment tous les exemples/tests de ce projet utilisent la forme statique, jamais le sucre, pour `Array`/`Map`.

Root cause structurel : `src/lower/expr.d/typeinfer.rs` (`expr_ir_type`) traite `Expr::StaticCall` et `Expr::Call{callee: Field}` comme **deux branches de match totalement indépendantes**, chacune avec sa propre logique de résolution de type — un correctif appliqué à l'une n'est jamais automatiquement répercuté sur l'autre. Même schéma probable ailleurs dans le lowering (boxing d'arguments, dispatch de méthodes) partout où statique et sucre coexistent pour un même builtin.

## Deux volets

1. **✅ Test immédiat — fait pour les 6 builtins à double forme.** `allows_instance_sugar` (`src/sema/typecheck.rs`) liste exactement 6 classes : `String`, `Array`, `Map`, `JSON`, `HTTPRequest`, `HTTPResponse` — aucune autre classe builtin n'a de sucre d'instance (les classes purement statiques comme `Math`/`Convert`/`System`/`IO` ne sont pas concernées, aucun risque de divergence).
   - `Array`/`Map` : bug RÉEL trouvé et corrigé (voir docs/roadmap.d/langage-array-get-display-bug.md) — `examples/tests/43_array_map_get_concrete_typeTest.oc` (19 assertions, statique + sucre).
   - `String`/`JSON` : **aucune divergence trouvée** — vérifié empiriquement (`trim`/`len`/`upper`/`lower`/`split`/`empty`/`encode` sur conteneurs concrets `float`/`bool`). Ces méthodes n'ont pas de type d'élément générique `T` à résoudre dynamiquement (contrairement à `Array`/`Map`), donc pas le même risque structurel — mais `String` n'avait AUCUNE couverture de test avant cet audit (ni statique ni sucre). Comblé par `examples/tests/44_string_json_sugar_parityTest.oc` (20 assertions).
   - `HTTPRequest`/`HTTPResponse` : un AUTRE type de divergence (pas lié à `elem_types`) avait déjà été trouvé et corrigé plus tôt dans ce projet — le sucre laissait passer `res.close()`/`req.status()` (mélange des deux côtés) sans le garde-fou que la forme statique imposait déjà (voir git log, `HTTP_REQUEST_METHODS`/`HTTP_RESPONSE_METHODS`). Pas de nouveau test dédié ajouté ici : ces méthodes n'ont pas non plus de type générique `T`, et une vérification supplémentaire nécessiterait un vrai appel réseau (même contrainte que `examples/builtins/http.oc`, qui n'est pas un test `ocaraunit` pour cette raison) — déjà exercées fonctionnellement par cet exemple, exécuté à chaque régression.
2. **✅ Structurel — `expr_ir_type` converge maintenant vers une résolution partagée.** Nouvelle fonction `resolve_method_return_type(builder, resolved_class, method, elem_type_source)` (`src/lower/expr.d/typeinfer.rs`) — SEULE source de vérité pour "quel est le type de retour d'une méthode (classe, méthode) connue", appelée à la fois par `Expr::StaticCall` (classe donnée directement, `elem_type_source` = premier argument) et par `Expr::Call{callee: Field}` (classe déduite du récepteur — logique de déduction elle-même INCHANGÉE, propre à chaque forme et non convergeable — `elem_type_source` = le récepteur lui-même). Élimine structurellement le risque qu'un correctif futur ne s'applique qu'à une seule des deux formes : toute évolution de cette logique (nouveau cas `elem_types`, nouvelle entrée `fn_ret_types`...) profite désormais automatiquement aux deux syntaxes. Pur refactor, AUCUN changement de comportement (vérifié : les deux branches produisaient déjà exactement `Ptr` dans tous les cas de repli, y compris la chaîne de noms codés en dur de l'ancienne branche `StaticCall`, dont les deux issues étaient identiques — code mort supprimé au passage). Vérifié par tous les tests de parité existants (39 assertions, comportement identique) + `make regression` intégral.

## Priorité

✅ Terminé — les deux volets (tests de parité pour les 6 builtins, convergence structurelle de `expr_ir_type`) sont faits et vérifiés.
