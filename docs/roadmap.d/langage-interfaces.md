# Interfaces

## ✅ Deux bugs corrigés

- **Import à symbole unique et interfaces transitives** : `import Circle from "fichier"` ne rapatriait que la classe nommée, sans jamais regarder sa liste `implements` pour ramener les interfaces qu'elle référence dans le même fichier source (`src/main.rs`). Confirmé par `examples/tests/11_interfacesTest.oc.bak`, qui contournait le problème en redéfinissant localement les interfaces plutôt que de les importer. **Corrigé** : le chargement d'une classe importée par son nom rapatrie désormais automatiquement toute interface de sa liste `implements` trouvée dans le même fichier.
- **Vérification de signature absente pour E09** : le check d'implémentation d'interface (`src/main.rs`) ne vérifiait que la présence d'une méthode du même nom, jamais sa signature. **Corrigé** : arité, types des paramètres et type de retour sont maintenant comparés (via `types_compat`/`type_name`), avec un message d'erreur dédié en cas de désaccord.

Vérifié manuellement (scripts de test ad hoc) : une classe qui implémente une interface définie dans le même fichier importé compile désormais sans avoir à réimporter l'interface explicitement ; une méthode dont la signature ne correspond pas à l'interface est maintenant rejetée à la compilation. `make regression` ne montre aucune régression.

## ✅ Polymorphisme réel à l'exécution (classes ET interfaces) corrigé

Le dispatch était **100 % statique par mangling de nom** — aucune vtable, aucune identité de classe à l'exécution. En creusant le dispatch d'interface, il est apparu que le problème était bien plus large que prévu : **aucune affectation polymorphe de classe à classe ne compilait**, même sans interface (`var s:Shape = use Circle()` était rejeté à la compilation). L'opérateur `is` ne distinguait pas non plus une classe d'une autre ni une classe d'une interface : `x is Circle` et `x is Drawable` compilaient en code strictement identique (`__is_object` seul). Après discussion, le chantier a couvert les deux cas (héritage de classe + interfaces), pas seulement les interfaces.

- **Identité d'objet à l'exécution** : le header de chaque instance de classe utilisateur passe de 8 à 16 octets (`[class_id:8][tag:8]`, même patron que l'extension `[len:8][tag:8]` d'`alloc_str`) — `__alloc_class_obj` (`runtime/src/lib.rs`) écrit désormais un `class_id` entier unique (`IrModule::class_ids`, attribué séquentiellement à la compilation) en tête de chaque objet, lu à l'exécution via `Inst::GetField{offset:-16}`.
- **Affectation polymorphe** : `types_compat` (`src/sema/typecheck.rs`) prend maintenant la table des symboles en paramètre et accepte `Type::Named(f)`/`Type::Named(e)` dès que `f == e` OU que `SymbolTable::class_matches(f, e)` (`src/sema/symbols.d/lookups.rs`) — qui remonte la chaîne `extends` de `f`, acceptant un match sur le parent OU sur une interface implémentée à N'IMPORTE quel niveau de cette chaîne (transitif, à la différence du diagnostic E09/du dispatch — justifié : une méthode héritée sans override hérite aussi de sa signature déjà validée par E09).
- **Dispatch dynamique réel** : deux nouveaux modules de lowering génèrent, pour chaque méthode d'instance potentiellement polymorphe, une fonction dispatcher séparée (des noms mangled existants restent inchangés, toujours nécessaires pour les appels `self`/parent et la copie de méthode héritée) :
  - `src/lower/builder.d/class_dispatch.rs` : `__dispatch_Classe_méthode`, candidats = la classe elle-même + tous ses descendants transitifs (`extends`).
  - `src/lower/builder.d/interfaces.rs` : `Interface_méthode` directement (ce nom n'existait jamais avant), candidats = les implémenteurs DIRECTS uniquement (même règle non transitive que E09).
  
  Chaque dispatcher est une fonction `IrFunction` construite à la main (pas issue du lowering d'AST) : une chaîne if/else sur le `class_id` lu en tête d'objet, un appel vers l'implémentation concrète du candidat correspondant, un retour défensif (zéro/vide) si aucun candidat ne correspond — normalement inatteignable, les invariants étant garantis par la sémantique. Un appel de méthode d'instance sur une variable/un champ dont le type déclaré a des sous-classes (`IrModule::classes_with_subclasses`) ou est une interface est redirigé vers son dispatcher plutôt que vers l'implémentation concrète du type déclaré (voir `src/lower/expr.d/lower.rs`) — SAUF pour un appel `self.méthode()`/`parent.méthode()` depuis l'intérieur d'un corps de méthode, qui reste résolu statiquement (limitation délibérée, voir plus bas).
- **`is ClassName`/`is InterfaceName` réel** : `lower_is_check` (`src/lower/expr.d/literals.rs`) construit désormais un vrai branchement (via `IrModule::is_check_candidates`, précalculé : elle-même + descendants transitifs pour une classe, implémenteurs directs pour une interface) — lit le `class_id` réel de l'objet et le compare à l'ensemble des candidats. Un nom inconnu (ni classe ni interface) retombe sur l'ancien comportement (`__is_object` seul), inchangé.
- **Bug pré-existant découvert et corrigé en cours de route** : la copie des méthodes héritées (`lower_class`, `src/lower/builder.d/classes.rs`) ne remontait qu'un seul niveau de `extends` — une classe à 3+ niveaux d'héritage dont un ancêtre intermédiaire n'override pas une méthode déclarée par un ancêtre plus lointain ne générait cette méthode pour AUCUNE classe intermédiaire/feuille (confirmé par une reproduction purement statique, sans aucun polymorphisme en jeu). Corrigé par une boucle remontant toute la chaîne `extends`, avec un `already_emitted` garantissant que la déclaration la plus proche l'emporte toujours.
- **SEGFAULT découvert et corrigé pendant les tests** : `n is Shape` où `n:int` (un entier concret, jamais boxé, arbitrairement grand) appelait `__is_object`/`read_tag` sans aucune vérification statique préalable — même classe de vulnérabilité que le SEGFAULT `read_tag` sur un `mixed` boxé corrigé plus tôt dans ce chantier, mais jamais couverte pour un entier concret. Corrigé par un court-circuit statique dans le lowering de `Expr::IsCheck` (`src/lower/expr.d/lower.rs`) : si la cible est un nom de classe/interface et que le type statique de l'opérande est `I64`/`F64`/`Bool` (jamais un pointeur), retourne directement `false` (après évaluation de l'opérande pour ses effets de bord) sans jamais appeler `__is_object`.

Vérifié : `make regression` — 495 PASS / 0 FAIL / 0 ERREUR(S), aucun indice de crash. Nouveau test de régression `examples/tests/39_polymorphismTest.oc` (14 assertions : dispatch de classe de base, sous-classe sans override, type exact, héritage 3 niveaux, méthode héritée d'un grand-parent jamais redéclarée, dispatch avec argument transmis, dispatch d'interface, `is ClassName`/`is InterfaceName` réels, `is` sur une valeur non-objet).

## Limitation délibérément non couverte

Un appel `self.méthode()` (ou vers `parent`) depuis l'intérieur d'un corps de méthode n'est **jamais** redirigé dynamiquement — il reste résolu vers l'implémentation concrète de la classe sous laquelle le corps a été lowered, quel que soit le type réel de l'objet à l'exécution. Seuls les appels externes (`obj.méthode()` depuis en dehors du corps de la classe) bénéficient du dispatch dynamique.
